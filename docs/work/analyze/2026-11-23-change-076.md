## 問題がなかった主な照合点

- Recent Experiencesは永続概念ではなく、直近EventからObservation要点、Tool signal、Action / failure、進展有無を組み立てる入力であるため、旧Run snapshot内の`recentExperiences[].steps[].action`を現行の導出入力へ復元する位置は一次仕様と一致する（`spec/personal-agent-implementation-design-v2.md:191-197`、FR-30）。
- `agent_runs`は同じEventに対するretryを含む実行attemptの判断入力・出力監査であり、Experience Integrationがsource Runを親として再構成する設計と矛盾しない（`spec/personal-agent-implementation-design-v2.md:296-298`、`docs/ARCHITECTURE.md:271`、NFR-7）。
- 変換はExperience Integrationのsnapshot読取り境界だけで、新規Action writer、現行Action schema、DB schema、配送routeを旧形式へ戻していない。旧peer名やDiscord IDを配送先に復活させない方針はFR-92 / ADR-24と一致する。
- 正常な旧peer Actionのunit testと、実repositoryのpending復元を通るintegration testが追加されている。
- 旧Peer Response契約は局所的なstrict Zod schemaとして再現され、Action外側は`type`、任意`content`、`peer`だけ、peer内側はtrim後1〜120文字の`name`とtrim後1〜6,000文字の`content`だけを許可する。合格後に現行の`{ type, content }`を新規構築するため、空白、上限超過、未知field、新旧field混在は現行strict schemaへ残して拒否され、NFR-8とIssueの受け入れ条件を満たす（`src/infrastructure/persistence/postgres-experience-integration.ts:13-18,30-49`、`tests/unit/experience-integration.test.ts:16-43`）。
- Issueは、限定readerを`agent_runs`の歴史的監査snapshotの読取り境界として維持し、旧writer・旧配送経路は維持しないと明記した。現行Domain契約へ旧writerや旧DB schemaを戻さないため、一次仕様の恒久的な旧API / 旧DB schema互換の非目標と両立する（Issue 076 Scope）。
