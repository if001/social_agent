## 第2回レビュー指摘（履歴。すべて解消済み）

### HIGH 2（残存）: Toolなしretry後のbackfillが旧traceを復活させる

- `scripts/backfill-reflection-tool-executions.ts:34,39` の既存relation除外は、Toolなしで成功したscopeを識別できない。
- 具体的には、旧writerでTool付き失敗→新writerのretryがToolなしで成功→Session完了→backfill実行、という経路では新relationが0 rowなので旧JSONが投入される。`reflection_attempts` / `reflection_memory_batches` の更新は依然旧 `tool_executions` を残す。Session完了済みのためunfinishedチェックにも止められない。
- runtimeで処理済みscopeの旧JSONを無効化するか、relationが0 rowでも切替を判定できるmarkerが必要。新relationが存在するケースと単純な二度実行のtestだけでは不足する。

### HIGH 3（残存）: refreshで保存anchorを落とし、retry時に親snapshotを上書きする

- `src/infrastructure/persistence/postgres-reflection.ts:125-145` の `refresh` は `reconciliationAnchors` を返さない。
- retryで `load` が保存anchorを復元しても、`src/application/reflection.ts:209-211` のMemory completedスキップ直後に `refresh` がこれを落とす。その後 `reconciliationInput` は未保存と判定してanchorを再選択し、親 `input.reconciliationAnchors` を上書きする (`postgres-reflection.ts:207-208`)。
- 途中までanchorを完了したSessionでは、再選択が完了anchorを除外するため、そのanchorの更新前の完全本文が監査snapshotから消える。残りanchorも新たな候補や内容へ変わり、固定入力retryにならない。親に一度保存したanchor一覧をrefreshとretryで維持し、未完了IDだけを実行対象として絞り込む必要がある。
- また、前回指摘した後続targetの `refresh` 後のMemory/Stateは、開始時親snapshot＋selectorに対応する保存版をまだ持たない。Session内で更新された後の入力も監査再構成できるよう確認が必要。
- 追加された実DB testは初回selectionの保存と単一anchor commitまでで、`load→Memory completed→refresh→reconciliationInput` を通すretryを検証していない。

## 初回指摘（履歴）

### HIGH 1: Memory batch失敗時に同じTool callを二重保存し、成功retry後も古い失敗traceが残る

- 箇所: `src/infrastructure/persistence/postgres-reflection.ts:306-308,332-335`、呼出元 `src/application/reflection.ts:217-219`。
- Memory ReflectorがTool実行後に失敗すると、`failMemoryBatch` がbatch scopeへ書いた同じtraceを、続く `failTarget(input, "memory", error)` がbatchなしscopeへ再度書く。したがって1 call 1 rowにならない。
- retryでbatchが成功しても `commitMemoryBatch` はbatch scopeだけを置換し、`completeMemoryTarget` はtarget scopeの失敗traceを消さない。完了SessionのDebug UIにも前回失敗callが残り、call数と成功/失敗監査が誤る。
- Memory target失敗は集約statusだけを更新し、callの所有scopeをbatchへ一意化する必要がある。実PostgreSQLで「Tool付きbatch失敗→成功retry→各callが一度だけ存在し、旧traceがない」を検証する。
- 対応要件: FR-41 / FR-42 / FR-81 / NFR-7、Issueの1 call 1 rowと同一scope置換。

### HIGH 2: backfillが新writerのtraceへ古いJSONを再追加する

- 箇所: `scripts/backfill-reflection-tool-executions.ts:30-36,48-50`。
- 新writerは既存 `tool_executions` JSONを消去しない。既存の失敗scopeを新writerでretryした後にbackfillを実行すると、scriptは古いJSONも対象にして、新writerと異なる `reflection-tool-backfill:...` IDで挿入する。`ON CONFLICT (id)` はscopeやcallの重複を防がない。
- 新traceへ旧traceが混入するほか、一度backfillしたscopeをretryで置換した後にbackfillを再実行すると、消した旧traceが復活する。Toolなしの成功retryでも同様である。
- 新writerへ切替済みかをscope単位で識別し、そのscopeの旧JSONを再投入しない仕組みが必要。新traceあり/Toolなしretry後/再backfillのケースを実DB testへ追加する。
- 対応要件: FR-41 / FR-42 / NFR-7、Issueのbackfillとretry監査。

### HIGH 3: selectorの参照先が親snapshotに存在せず、Reflectorが読んだ内容を再構成できない

- 箇所: `src/infrastructure/persistence/postgres-reflection.ts:375,380-381`。関連: `load` のMemory読取り (`:103-115`)、`refresh` (`:125-145`)、`reconciliationInput` (`:148-202`)。
- `reflection_runs.input` はSession開始時の最新32 Memory等を一度保存する。一方、Reconciliationは別の最大64 Memoryからanchorを選び、後続targetは `refresh` 後のMemory/Stateを読む。この差分で子inputの本文をIDだけへ変更したが、その追加・更新後の内容は親snapshotへ保存していない。
- 例えば最新32件の外にあるdistant anchorを選んで更新すると、親inputにanchorがなく、子inputにはIDだけが残る。resolverの `query_summary` は240文字の切詰めであり、更新前の完全な本文・significance等を復元できない。Relation Toolを呼ばないReflectorでも発生する。
- 子の重複snapshotを戻すのではなく、親側の参照可能な入力断面/差分に必要な内容を一度保持し、selectorがその保存版を指すようにする必要がある。親の開始時32件にないanchorと、Session内更新後の後続targetで監査再構成を検証する。
- 対応要件: FR-41 / FR-42 / FR-79 / NFR-7、設計ノート「何を読んで何を決めたかを再構成できる」とIssueの親snapshot＋selector。
