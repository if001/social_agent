# Issue #038 レビュー

対象：`issues/038-design-persistence-model-and-drizzle-refactor.md`、`docs/work/note/2026-11-14-persistence-model-design.md`、後続Issue #039〜#045。

## HIGH

1. 全runtime tableのowner / reader / writer / retentionと、本番query call site約240件のDrizzle / PostgreSQL専用SQL / migration scriptへの割当てが未完成である。これでは#040/#044で移行漏れを検出できない。
2. `events`を論理Eventとretry executionの両方に使うと、同一観測のretryが複数のEvent Experience、Memory Formation、Reflection検索対象となる。論理Eventとattemptの境界、Experienceを成功Eventごとに一度だけ形成する規則が未決である。
3. data migrationに、旧列ごとの旧→新mapping、意図的な非移行、active work itemの変換、dry-run検証式がない。特にTool idempotency、State Change、Experience Integration、Web snapshot、Schedule / Prediction / Concern ActivityのRun参照を安全に切替えられない。

## MEDIUM

1. Experience更新時のProjection embedding stale化、再embedding、検索除外、model/dimension/error/attempt metadataが未定義である。
2. `event_subjects`の正規化元、検索必要性、subject master不在時の整合性、更新規則が未定義である。

## 結論

通常Eventの原観測と実行attemptを区別する必要がある。新tableを増やさず既存tableを活かすなら、`events`を不変の論理Event、`agent_runs`をEvent attempt / 入出力履歴として維持し、重複した所有者列と入力複写だけを削る案が有力である。方針を決め、query inventoryとdata migration mappingを完成させるまで、後続実装Issueへ進めない。

## 再レビュー（2026-11-14）

修正後の設計を独立に再確認した。`events`を不変の論理Event、`agent_runs`をretryを含むattemptとして分離し、ExperienceをEventごとに一度だけ形成する規則は一貫している。25ファイル・240 call siteのinventory算術、expand → data migration → reader → writer → contract/dropの移行順、列ごとのdry-run / `--apply` / 不整合停止条件も確認した。

G3の直接Projection作成だけがExperience→Projectionの一方向契約に反していたため、#041で直接writerを廃止し、検索対象のG3 EventもExperience Integration経由に統一する、と設計決定した。一次文書への反映と`spec-analyze`は#039の完了条件として残る。
